# 架构说明

LightWake 的源码位于 `apps/screen-guard`，负责自动熄屏、唤醒后的倒计时，以及恢复正常使用。

## 屏幕工具

只有一个 AppKit 程序：`轻醒.app`（bundle id `local.xy.lightwake`）。它常驻运行
（`LSUIElement` + `.accessory` 激活策略，装到「应用程序」后随登录启动），同时是熄屏模式、
设置面板和按键规则的执行者 —— 靠**怎么被唤起的**分派，没有“角色”这回事了。

| 文件 | 职责 |
| --- | --- |
| `GuardState.swift` | 纯状态机，接收单调时钟时间与屏幕睡眠 / 唤醒事件，输出提示、数字倒计时、熄屏等阶段。 |
| `ScreenGuard.swift` | 熄屏模式控制器：提示窗口、收起动画、电源声明和系统事件监听。菜单栏不在这里，见 `Main.swift`。 |
| `ControlStore.swift` | 用模式令牌和跨进程文件锁协调开启 / 关闭操作。 |
| `Main.swift` | 唯一入口：菜单栏图标与设置入口、双击 / URL 分派、`lightwake://` 规则执行、登录项注册。 |
| `ScreenButtonState.swift` | “该关还是该开”的**唯一**判断：正常亮屏启动倒计时，倒计时 / 熄屏 / 锁屏选择保持亮屏。 |
| `ScreenButtonController.swift` | 协调取消令牌、唤醒及执行对应规则的应用 / 文件夹目标。 |
| `ScreenInputRules.swift` | 版本化的按键规则、冲突校验和映射调用协议；只读识别现有 Karabiner 入口。 |
| `ScreenInputRuntime.swift` | 用户启用后监听指定键盘 / 鼠标按键；监听器安装、权限请求与退出。 |
| `InputRulesSettingsView.swift` | 选择 / 录制按键、配置各自目标、保存和删除规则。 |
| `QuietProtectionSettings.swift` | 按键规则和使用说明，提示 Codex 桌面及历史记录相关操作可能亮屏；不提供保护开关。 |
| `QuietProtection.swift` | 拒绝启用已下线的进程暂停机制，并关闭旧版开启选择。 |
| `resources/quiet-desktop/` | 只读状态检查、任务调用包装器及旧版暂停记录清理程序。 |

### 一个动作，两个方向

3.0 之前是四个 app（关闭屏幕 / 开启屏幕 / 轻醒按键 / 轻醒设置），同一个可执行文件各存一份、
靠 `Info.plist` 里的 `ScreenGuardRole` 分工。其中前三个其实是同一个函数的两端：
它们都在问 `ScreenButtonState.action(guardActive:session:displayAsleep:)`，只是各自只会走
一边（`.startCountdown` 或 `.keepScreenOn`）。合成单 app 之后，桌面按钮、菜单栏和按键规则
全部走这同一个函数，不再有第二份“该关还是该开”的判断。

它不是单纯取反：屏幕已熄或会话已锁时它选“保持亮屏”。这是刻意的安全偏置 ——
宁可多亮一次屏，也不要在用户看不到的时候开始倒计时关屏。会话不可用时什么都不做。

三个屏幕动作曾经是三个独立 bundle，靠 `openApplication(bundleID)` 互相启动。
现在它们是**进程内命令**（`ScreenInputContract.enterOffModeCommand` /
`exitOffModeCommand`）：`ScreenButtonController` 的接口仍然只认“一个字符串标识”，
应用层在注入的 `openApplication` 里把这两个符号拦下来、在本进程执行，其余标识照旧交给
系统打开。这样控制器的状态机和它的测试都不用为一个已经不存在的 bundle 让步。

### 计时与取消

双击「轻醒」（或菜单栏 →「关闭屏幕」）启动 5 秒窗口：前 3 秒显示提示，随后平移缩小到每块屏幕可见区域的左上角，余下 2 秒显示数字。动画不会额外增加总时长。

收到真实的 `screensDidSleepNotification` 后，下一次 `screensDidWakeNotification` 会启动新的 20 秒窗口。前 3 秒显示提醒，随后 17 秒显示角落数字；轮询、重复唤醒通知不会重置起点。计时使用 `systemUptime`，避免系统日期变化影响倒计时。

密码界面的显示器唤醒与成功解锁分别处理。锁屏或会话不可用期间，既隐藏桌面提示，也停止轻醒的关屏请求；5 秒初始期限、20 秒亮屏期限、旧重试和延迟的立即关屏动作均不能打断身份验证。显示器由 macOS 自身管理。确认会话恢复到桌面时，废弃旧期限，重新开始完整的 3 秒提醒和 17 秒角落倒计时。重复的解锁或唤醒通知不会续时。已通过再双击一次取消的模式也不会因解锁而恢复。

控制器监听锁定、解锁和会话切换通知，并在每次计时、显示器事件及最终关屏调用前读取 `CGSessionCopyCurrentDictionary`。这让过期定时器即使先于解锁通知送达，也能识别新的会话状态；最终检查在模式文件锁内完成。用户不在当前控制台或无法读取会话时暂停关屏操作，恢复桌面后再开始完整 20 秒。锁屏字段 `CGSSessionScreenIsLocked` 及 `com.apple.screenIsLocked` / `com.apple.screenIsUnlocked` 通知是当前 macOS 的未公开约定，系统升级后需验证。生命周期日志仅记录会话和显示器状态，不记录密码或模式令牌。

控制器在主线程处理计时与动作。到期通过 `/usr/bin/pmset displaysleepnow` 请求显示器睡眠；在尚未收到睡眠通知时，状态机会间隔 20 秒重试，不因延迟的计时回调连续发出命令。

运行中的熄屏模式持有 `PreventUserIdleSystemSleep` 电源声明，允许显示器关闭，同时阻止闲置触发整机睡眠。停止时释放声明；这不改变系统持久电源设置，也不替代系统的锁屏策略。合盖不在“停止”的触发条件里，详见 [README 的“合盖不休”一节](../README.md)。

退出熄屏模式时，先将本机模式文件写为 `off`，再发送分布式停止通知，并以短时 `caffeinate -u` 请求亮屏。模式令牌是最终依据：熄屏控制器会在每次执行前检查令牌，并通过同一把 `flock` 将最后一次检查和实际关屏命令串行化。取消写入完成后，旧令牌不能再触发关屏。运行状态位于当前用户的 `Application Support/ScreenGuard` 目录 —— 这个路径与 bundle id 无关，所以 3.0 换 id 没有丢状态。

提示是独立的 AppKit 非激活窗口，忽略鼠标点击，避免夺取当前应用焦点；角落数字是桌面窗口，不是菜单栏倒计时。系统锁屏界面不属于这些窗口的显示范围。

### 屏幕切换调用入口

按键监听进程由 launchd 用 `--listen` 拉起，跑的是同一份 `轻醒.app`，只是不装菜单栏图标。具体手柄和 Karabiner 映射由独立的手柄项目维护，映射可打开对应规则的地址；3.0 之前那条打开“轻醒按键.app”的调用仍有兼容入口。

控制器同时检查模式文件和“熄屏模式是不是真的在跑”，避免遗留令牌被误判为活动倒计时。切换规则在正常亮屏时进入熄屏模式；恢复亮屏时，先在原有文件锁下写入 `off`、发出停止通知并执行短时 `caffeinate -u`，随后退出熄屏模式，保存触发规则自己的应用 / 文件夹目标。锁屏身份验证仍由系统处理。应用启动期间的后续规则串行处理；同一规则短于 180 毫秒的重复事件合并。

只有存在待执行目标时，按键控制器才启动 200 毫秒状态轮询。锁定、会话不可用或显示器仍熄屏时不打开目标；确认解锁且屏幕已亮后再等待至少 600 毫秒连续稳定状态，让密码界面退出，随后执行一次并清除目标和定时器。轮询不请求唤醒或解锁。后续有效规则替换先前目标，重新熄屏或规则被修改 / 停用 / 删除时取消旧目标。每次轮询都重新检查模式文件和保存的规则，普通亮屏或解锁没有待执行目标时不打开应用。

监听器只在用户启用键盘或鼠标规则后安装，登录时使用 `--listen` 启动，不执行屏幕切换。它使用经过系统授权的只读事件监听，不吞掉按键、不保存输入历史。映射规则使用 `lightwake://trigger/<规则 ID>`，仅接受已保存并启用的映射类型规则；不接受附带的命令或目标参数。详细约定见 [按键规则与调用接口](input-rules.md)。

## 打包

2.5.2 已撤下直接冻结 Codex 电脑操作服务的方案。应用启动时调用关闭逻辑，撤销旧版开启选择；新安装不创建此功能的目录或后台任务。新版脚本不再获取暂停所有权，并在进程信号边界拒绝 `SIGSTOP`，只允许在桌面状态符合检查时清理旧的自有暂停记录。完整因果链尚未从卡死现场取得，不能将这次撤下描述为已经通过真实解锁验收。

`build_local.py` 使用当前 Xcode 的 Swift 编译器构建同一份程序，生成**唯一一个** `轻醒.app`，身份来自 `resources/LightWake-Info.plist`。3.0 之前是同一份可执行文件配四份角色 plist 生成四个 app，那些 plist 已删除。2.5.4 移除防亮屏设置入口和 Codex 候选补丁；`quiet-desktop` 资源只保留兼容旧任务所需的只读检查及退出清理，现在每个构建都带上（以前只有设置 app 带）。构建过程不安装、启动防护或写入用户选择。`MakeIcons.swift` 仍绘制两款图标（深蓝色显示器与月亮、绿色显示器与电源符号），单 app 用前者。构建不依赖已经安装的应用。

工具链由 `scripts/swift_toolchain.py` 定位：平时走 `xcrun`，Xcode 跨大版本升级后 `/usr/bin` 下的 `swiftc` / `lipo` / `cc` 这些 shim 会因许可证未同意而失败，这时退回直调 Xcode 包里的真实工具链，并替它补上 SDK 参数（`-sdk` / `-isysroot`）。两条路给出同一套工具，产物没有区别。根治办法是在终端里跑一次 `sudo xcodebuild -license accept`。

应用包采用本机临时签名，用于自行构建和本机安装；当前流程不包含 Developer ID 公证或 App Store 分发。

## 验证范围

根目录的 `scripts/test.py` 汇总计时状态、模式存储、控制器集成检查和装机脚本。集成检查通过可替换的时钟、提示和关屏动作验证行为，不实际执行关屏。`--visual` 额外运行真实提示窗口和动画检查。

装机脚本的检查（`scripts/tests/test_install.py`）把 `install.py` 当模块加载、把它的 `BUILD` / `ARCHIVE` 指到临时目录，所以跑的是生产函数本体：首次装机、覆盖装机、签名自检失败后的回滚（含首次装机失败不留半装）、构建产物不齐时的事前拦截、按钮幂等与指错自修复、以及 3.0 之前四个 app 与四个按钮的归档。全程不碰真的「应用程序」和桌面。造“签名坏了”的现场要在签完名之后再改 `Info.plist` —— codesign 把 plist 的哈希封进了签名。

兼容检查覆盖新安装无副作用、旧开启配置不能重新冻结服务、启动时关闭旧选择，以及旧暂停记录的清理和 PID 复用。进程信号测试只操作临时编译的独立测试进程，不连接真正的 Codex 电脑操作服务。设置布局检查确认 Codex 亮屏提示可见、保护入口已移除且文字不截断，不显示窗口。详细约定见 [桌面调用与旧版清理](quiet-protection.md)。

这些检查覆盖代码路径，不能代替不同 macOS 版本、硬件和多显示器环境中的实际安装验证。`scripts/build.py` 构建轻醒，并检查生成应用的签名。

解锁回归验收：启用自动熄屏，等系统要求密码后唤醒并解锁。桌面应直接显示新的 20 秒提醒，3 秒后显示角落数字 17；解锁前消耗的时间不得导致桌面提前关屏。再次测试重复唤醒通知及锁屏期间取消模式，确认它们不会延长计时或重启已取消的模式。
